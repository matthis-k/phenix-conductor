## Decisions

- #503 is on main. Reuse its generic `CallableRef` and dispatcher rather than callback-specific transport.
- Admissions are ephemeral and generation scoped; the backend sees only ordinary `CallableDescriptor`s through `ToolProvision`.
- One ACP callback queue serves one client connection, so admission and invocation accept only that owner and generation.
- Provider adapters translate the backend-neutral model tool surface at the protocol boundary; providers do not gain a client-tool-specific path.
- `ToolProvision` stays origin neutral; admission ownership remains above the backend boundary.
- Session admission descriptor projection is deterministic by callable id before backend presentation.
- The application host owns the admitted-client execution adapter: permission runs before generic callable dispatch, while ACP transport remains a transport concern.

## Findings

- #505 is based directly on main after #503.
- Exact-head CI before the latest implementation commit was blocked before jobs start with GitHub `action_required`; there were no job logs to inspect.
- This worker environment has no GitHub write credential or GitHub connector. `git push origin HEAD:spec/client-provided-tools` cannot authenticate, so the local commit is the current recovery point.
- Transport closure permanently retires the client owner generation. A new service starts with an empty admission registry.
- Generic capability dispatch validates callable contract/input before provider code and validates output before release. Cancellation and disconnect remain structural errors.
- ACP application operations already admit, list, invoke, and remove client tools through the generic capability registry.
- The execution/model path carries backend-neutral tool descriptors and typed `ModelToolCall`s, but the agent loop currently returns tool calls without executing them.
- `ToolProvision::merge_callables` is origin neutral and rejects duplicate ids, but no production session/model assembly currently joins admitted client descriptors with runtime/plugin descriptors before provisioning.
- `phenix-binding-lua` already lifts Lua functions into client-owned `CallableRef`s and routes fixed application operations through `_invoke_application`; `phenix.tools.register` still needs to compose those mechanisms without another callback registry.
- The application host now has `execute_admitted_client_tool_call`: it resolves a model-emitted call against the session admission, invokes the ordinary permission callback before dispatch when required, preserves the model call id, then routes through `InvokeCallable` and emits the existing `ExecutionChange::ToolResult` or `ToolFailed` variants. Regression coverage proves denial prevents callback dispatch, allow reaches generic capability dispatch, and permission-free tools skip the permission callback.
- `SharedCapabilityRegistry` already supports single-reference `unregister`; explicit client-tool removal should use it so a removed raw callable cannot remain directly invokable until whole-generation retirement.
- Added a public integration regression that retires the old client generation, proves the old callable is stale, re-admits the same tool id with a new generation, and invokes the new callable successfully.
- Explicit removal now unregisters the lifted callable after its final admission disappears. A callable admitted to another session remains live until that admission is removed.

## Tried / rejected

- A local checkout is unavailable in this worker environment because direct GitHub network access is disabled. Use repository CI for compilation/format evidence after pushes; do not infer local validation that did not run.
- Do not wire client-tool execution through the legacy backend boundary alone: the active execution/model path is the plugin model-routing ABI, and it currently lacks the production admission/invocation join.
- Do not add a client-specific backend tool protocol. The host adapter consumes the existing `ModelToolCall` and application permission/callable contracts.
